
## 这一趟真正在验的是压缩

上下文压缩（三级 + 一个空着的第四级）是这一趟第一次在全量上跑：

| | |
| --- | --- |
| 压过的执行单元 | 20,201 |
| 降级发出去 | 2,524 次 |
| 落在哪一级 | l1 少数、l2 绝大多数、l3 个位数 |
| 压失败 | 0 |
| 最后那道闸动手（上下文对不上就摘） | 0 |
| 压到 l3 仍超阈值 | 52 次，集中在三道超长题 |
| 因此撞上那一端天花板（400） | **2 次**（`mobly` ask#224、`updo` ask#196） |

`press_l3` 有 19,878 行而 `press` 有 20,201 行 —— 323 格压出了跟别人一样的话，
自动落在同一行上，读的时候只出一次。

两次 400 的形状一样：压到最狠一级还是装不下（`still 1068388 tok at l3, over 900000`），
照发，那一端按 token 数拒，只超出天花板 0.2%。**原因是结构性的**：能压的只有已经收口
的节点，而正在出的那个节点原样不动 —— 一道题跑到后期，当前节点自己就比所有收口节点
加起来还大。

## 中途改了两处，所以这 112 道不是一个批次

跑到一半发现两个真 bug，都是压缩带出来的，改完把受影响的题清库重跑：

1. **补齐排在了压缩后面。** 「模型调了工具但没人跑，补一条『没跑成』」这一步，
   拿到的是压过的那份 —— 而压过的那份里工具结果已经是文字，它认不出谁答过，
   该补的漏掉；更糟的是它只要补了任何一条，就回头重读原文返回，压缩白做，
   而原文里那个悬空的调用一路发出去，SDK 本地就拒：`Tool result is missing for
   tool call …`。**8 站栽在这儿，全是交卷站。**
2. **错误只打了最外层那一句。** 真正的原因挂在 `cause` 上，于是十几条错误长得
   一模一样，查不下去。

修法：补齐提到压之前、对原文做，压完不再重读；压完加一道闸，调用和结果对不上就
**摘掉那一小段**（不回退到原文）；错误连 `cause` 和那一端的 `responseBody` 一起打。

所以库里这 112 道：**53 道跑在修之前**（它们都通过了，没受影响），**59 道跑在修之后**。
修完那 6 个多小时里，孤儿调用 0 次、闸动手 0 次。

## 三条口径，读数的时候要知道

1. **时限是两小时，不是官方的三小时**（`task.toml` 的 10800 取小到 7200），
   所以这个 91 跟榜上的数不是同一个实验。
2. **`oxvg` 的 1 分是钟响之后落地的。** 到点不是硬切：已经出门的那一站会跑完，
   它的判卷在 `expired` 三分钟后回来，判了通过，状态从 failed 翻回 done。
3. **`go-genai` 没有重跑。** 它在上一趟里是干净输掉的（全程零异常、跑满两小时），
   按「没踩过异常的就算了」留着。
